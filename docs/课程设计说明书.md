## 1. 课程设计任务概述

本课程设计基于开源大数库 **NTL**（http://www.shoup.net/ntl），使用 C++ 实现以下五个任务：

1. **RSA 加密和签名**：密钥生成（p、q 均为 1024 比特素数）、加密、解密、密钥格式转换、签名与签名验证；
2. **Elgamal 加密和签名**：密钥生成、加密、解密、签名与签名验证；
3. **简单证书方案**：证书 `Cert(Alice) = (ID(Alice) || ver_Alice || s || ID(TA) || flag1 || flag2)`，
   其中 `s = sig_TA的私钥(ID(Alice) || ver_Alice)`，`flag1` 标识签名算法（0=RSA，1=Elgamal），
   `flag2` 标识公钥用途（0=加密，1=签名），证书采用 txt 格式；
4. **简易 PKI 系统**：教材 12.3.1 节严格层次 PKI 系统的简易版本——根 CA（自签名）下挂两个下级 CA
   （CA1、CA2），用户证书由下级 CA 签发；实现可公开查询的证书库（存储 CA 发来的证书，按证书所有者 ID
   返回证书路径 `<CA_root 证书，CA1 证书，Alice 证书>`），并给出一个使用例子
   （Alice 发送消息与签名，Bob 查询并验证证书路径后用证书中的公钥验证签名）；
5. **简易安全邮件系统**：无需网络传输。发送端查询接收端加密公钥证书链并验证、对邮件 Hash 签名、
   用接收端加密公钥加密 `m||s` 并发送；接收端用加密私钥解密、查询发送端签名公钥证书链并验证、
   用发送端签名公钥验证签名。

不同对象（TA、CA、证书库、Alice、Bob 等）完成的任务均用**独立的模块**（独立的类与源文件）完成，
并非用几个独立的程序完成。对以上方案和协议均有独立的测试函数。

## 2. 程序设计说明

### 2.1 总体结构与模块划分

项目使用 CMake 构建，C++17 标准，依赖 NTL / GMP（位于 `third_party/local`）。源文件结构如下：

```
src/
|-- crypto/                     # 加密与签名引擎（已有）
|   |-- crypto_engine.h/.cpp    # 抽象接口：PublicKey/PrivateKey/Keypair/EncryptionEngine/SignatureEngine
|   |-- rsa_engine.h/.cpp       # RSA 密钥生成、加密解密、签名验证、密钥格式转换
|   `-- elgamal_engine.h/.cpp   # Elgamal 密钥生成、加密解密、签名验证
|-- hash/
|   `-- sha_256.h/.cpp          # SHA-256（FIPS 180-4），用于签名时对消息取 Hash
|-- certificate/                # 证书方案与 PKI 基础设施模块
|   |-- certificate.h/.cpp      # 证书对象、txt 序列化、公钥文本转换、证书/证书路径验证
|   |-- trusted_authority.h/.cpp    # TA 模块：为 Alice 颁发简单证书
|   |-- certificate_authority.h/.cpp # CA 模块：根 CA 自签名、为下级 CA 和用户签发证书
|   `-- certificate_library.h/.cpp  # 证书库模块：只存储验证通过的 CA 证书，按 ID 返回证书路径
|-- pki/
|   `-- pki_user.h/.cpp         # 用户模块（Alice/Bob/Eve）：加密/签名密钥对、向 CA 申请证书
|-- mail/
|   `-- secure_mail.h/.cpp      # 安全邮件模块：发送端/接收端完整流程（m||s 编码、加解密、验证）
`-- demo/
    `-- umbra_demo.cpp          # 演示程序（可执行程序）
```

模块依赖关系：`umbra_mail` → `umbra_certificate` → `umbra_crypto` → `umbra_hash`。
各对象（TA、CA、证书库、用户、邮件系统）的任务分别由独立模块完成；证书模块不再定义自己的
算法枚举或引擎工厂，证书中的签名算法（flag1）直接复用 `crypto::CryptoType`
（0=RSA，1=Elgamal），抽象类只保留在底层的 crypto 引擎接口中，上层证书/TA/CA/证书库/用户/
邮件各模块均为普通的具体类与函数。

### 2.2 RSA 加密与签名设计（任务 1）

- **密钥生成**：随机生成两个 1024 比特素数 p、q（`NTL::GenPrime_ZZ` 内部执行足够多次
  Miller-Rabin 素性检测，保证通过检测的数是素数的概率足够高），取 `e = 65537`，
  计算 `λ = lcm(p-1, q-1)`，`d = e^{-1} mod λ`。公钥 `(n = p·q, e)`，私钥 `(p, q, d)`。
- **加密/解密**：将明文按 `NumBytes(n) - 1` 字节分组，每块转为大整数后做
  `c = m^e mod n`，输出格式为每行 `块长-c`；解密 `m = c^d mod n`。
  对解密/验证时来自外部（密文、签名文本）的大整数先约化到模数范围内，避免
  NTL 的 `PowerMod`/`InvMod` 对越界输入直接终止程序，保证篡改输入时只返回
  失败结果而非崩溃。
- **格式转换**：`PublicKey(const std::string&)` / `operator std::string()` 实现
  公钥 `n\ne`、私钥 `p\nq\nd` 与文本的互转。
- **签名/验证**：对消息取 SHA-256 Hash 值 H(m)，`s = H(m)^d mod n`；
  验证时恢复 `H(m)' = s^e mod n`，与本地计算的 H(m) 比较。

### 2.3 Elgamal 加密与签名设计（任务 1）

- **密钥生成**：生成安全素数 `p = 2q + 1`（q 为素数），取二次剩余子群的生成元 α（阶为 q），
  私钥 a 随机取自 `[1, q-1]`，公钥 `β = α^a mod p`。公钥 `(p, α, β)`，私钥 `(p, α, a)`。
- **加密/解密**：每块 `m`，取临时密钥 k，计算 `c1 = α^k mod p`、`c2 = m·β^k mod p`，
  输出 `块长-c1-c2`；解密 `m = c2·(c1^a)^{-1} mod p`。
- **签名/验证**：对 H(m)（约化到模 q），取 `gcd(k, q) = 1` 的随机 k，
  计算 `r = α^k mod p`、`s = k^{-1}(H(m) - a·r) mod q`；验证 `α^{H(m)} ≡ β^r·r^s (mod p)`。
  验证时对签名文本中的 `r` 先约化到模 p 范围内，因此用错误公钥验证签名只会返回
  “不通过”，而不会触发 NTL 内部错误。

### 2.4 简单证书方案设计（任务 1）

证书格式（txt）：

```
BEGIN UMBRA CERTIFICATE
ISSUER:TA
SUBJECT:Alice
ALGORITHM:RSA
PURPOSE:Encryption
PUBLIC_KEY:RSA <n> <e>
SIGNATURE:
<s>
END UMBRA CERTIFICATE
```

- 被签名的内容 `signed_payload() = ID(Alice) || ver_Alice`（即 `SUBJECT` 行与 `PUBLIC_KEY` 文本
  的拼接），签名 `s = sig_TA的私钥(signed_payload())`；
- `ALGORITHM`（flag1）：0=RSA，1=Elgamal（直接使用 `crypto::CryptoType` 枚举，值与之对应，
  不再单独定义算法枚举）；
- `PURPOSE`（flag2）：0=加密，1=签名（`KeyPurpose` 枚举值与之对应）；
- 公钥文本首行为类型标记（`RSA` 或 `ELGAMAL`），使证书中可存放任意一种公钥；
- 验证：`ver_TA的公钥(signed_payload(), s) == true` 则证书可信（`verify_certificate_signature`）；
- TA 模块（`TrustedAuthority`）在构造时生成自己的签名密钥对，`grant_certificate` 负责签发证书，
  支持 RSA 与 Elgamal 两种签名算法，`register_user` 登记用户信息。

### 2.5 简易 PKI 系统设计（任务 4）

层次结构（教材 12.3.1 节）：

```
CA_root（证书由自己签发，自签名）
 |-- CA1 -- Alice, Eve
 `-- CA2 -- Bob
```

- **CA 模块**（`CertificateAuthority`）：每个 CA 持有自己的签名密钥对；
  `self_sign()` 为根 CA 生成自签名证书；`issue_certificate()` 为下级 CA 或用户签发证书
  （签发者用自己的私钥签名 `ID(subject) || ver_subject`）。
- **证书库模块**（`CertificateLibrary`）：只存储由 CA 颁发且签名验证通过的证书——
  自签名证书必须为受信根 CA 的证书，其余证书必须由其签发者（证书已在库中）的公钥验证通过；
  查询接口按证书所有者 ID 返回证书路径（证书链）：从叶证书沿签发者逐级向上直至自签名根证书，
  即 `<CA_root 证书, CA1 证书, Alice 证书>`；另提供按 `(ID, 用途)` 的查询供邮件系统使用。
- **证书路径验证**（`verify_certificate_path`）：先用受信根公钥验证根证书（自签名），
  再逐级用上一级证书中的公钥验证下一级证书的签名。
- **使用例子**：Alice 用其签名私钥对消息签名；Bob 在证书库中查询 Alice 的证书路径，
  验证路径正确后，取出 Alice 证书中的签名公钥验证 Alice 的签名。

### 2.6 简易安全邮件系统设计（任务 5）

`m || s` 的编码采用“长度前缀”方式：`signed_mail = to_string(len(m)) + '\n' + m + s`，
其中 `s = sig_发送端签名私钥(SHA-256(m))`。

- **发送端流程**（`mail::send_mail`）：
  1. 在证书库中查询接收端的**加密公钥**证书链，并验证证书链是否正确；不正确则抛出异常，
     由交互层决定重新申请证书链或退出；
  2. 用发送端签名私钥对邮件 m 的 Hash 值签名得到 s；
  3. 从接收端证书链的叶证书中取出接收端的加密公钥；
  4. 用接收端加密公钥加密 `m||s` 得到密文 c；
  5. 返回（发送）c。
- **接收端流程**（`mail::receive_mail`）：
  1. 用接收端加密私钥解密 c，得到 `m||s`；
  2. 在证书库中查询发送端的**签名公钥**证书链并验证；
  3. 从叶证书中取出发送端的签名公钥；
  4. 用发送端签名公钥验证签名，返回恢复出的邮件内容 m。

## 5. 课程设计总结

本课程设计在已有 RSA / Elgamal 加密签名引擎（基于 NTL）的基础上，新增实现了简单证书方案、
严格层次 PKI 系统（CA 模块、证书库模块、用户模块）与简易安全邮件系统，所有对象均以独立模块
实现，每个方案和协议都有独立的测试函数，并提供了统一的演示程序（支持文件方式输入）。

设计要点与体会：

1. 证书中被签名的内容固定为 `ID || 公钥文本`，签发与验证使用同一 `signed_payload()`，
   保证了签名的可验证性；
2. 证书公钥文本携带类型标记（RSA/ELGAMAL），使证书链验证时能够正确解析各级公钥，
   支持 RSA 与 Elgamal 混合使用；
3. 证书库在入库时即对证书做“链接到受信根”的验证，只存储 CA 发来的合法证书；
   查询返回完整证书路径，验证由使用方（Bob / 邮件系统）完成；
4. 邮件系统按任务书流程分为发送端与接收端两套流程，`m||s` 采用长度前缀编码，
   可正确传输含换行的多行邮件；任何一步（证书链、签名）验证失败都会拒绝处理。
