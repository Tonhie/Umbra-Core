## 1. 任务要求与实现范围

任务书把课程设计组织为一条从公钥算法到安全邮件的实现链。算法层要求实现 RSA 和 ElGamal 两种公钥体制，并分别完成密钥生成、加密、解密、签名和签名验证。证书部分要求构造简单证书

```text
Cert(Alice) = ID(Alice) || ver_Alice || s || ID(TA) || flag1 || flag2
```

其中，`s` 是可信机构对 `ID(Alice) || ver_Alice` 的签名，`flag1` 指出签名算法，0 表示 RSA、1 表示 ElGamal，`flag2` 指出证书中公钥的用途，0 表示加密、1 表示签名。证书采用 txt 格式保存，并且两种签名算法都需要能够用于签发和验证。

PKI 部分按照教材 12.3.1 节的严格层次组织实体：根 CA 自签名，两个下级 CA 由根 CA 签发，用户证书由下级 CA 签发，证书库公开提供按用户 ID 的查询并返回完整证书路径。当前演示采用如下固定拓扑：

```text
CA_root
├── CA1
│   ├── Alice
│   └── Eve
└── CA2
    └── Bob
```

安全邮件部分不依赖网络传输。发送端使用签名私钥对邮件摘要签名，再使用接收端的加密公钥加密邮件和签名；接收端使用自己的加密私钥解密，查询并验证发送者的签名证书链，最后使用发送者公钥验签。任务书还要求不同对象由独立类和源文件实现，并为各方案提供独立测试函数。当前项目把这些类编译到同一组库和演示程序中，符合“模块独立、程序不必拆分”的要求。

本项目的交互演示增加了一个轻量 ASCII TUI。它不改变任务书规定的密码协议，只把密文保存在进程内的本地投递队列，让演示者可以选择用户、撰写邮件、发送、切换收件箱和阅读邮件。右侧日志只显示操作过程、算法、对象和长度等审计信息，不显示密钥、证书、明文、签名或密文的实际数值。

## 2. 总体设计与模块关系

项目使用 C++17，底层大整数运算由 NTL 完成，NTL 的 GMP 后端负责高精度整数支持。库按单向依赖组织：`umbra_mail` 依赖 `umbra_certificate`，`umbra_certificate` 依赖 `umbra_crypto`，`umbra_crypto` 依赖 `umbra_hash`。演示程序 `umbra_demo` 位于最上层，调用这些库完成批处理演示和交互式邮件演示。

```text
umbra_demo
    │
    └── umbra_mail
            │
            └── umbra_certificate
                    │
                    └── umbra_crypto
                            │
                            └── umbra_hash
```

`umbra_hash` 提供一次性和流式 SHA-256 接口。`umbra_crypto` 定义 `PublicKey`、`PrivateKey`、`Keypair`、`EncryptionEngine` 和 `SignatureEngine` 等公共抽象，并由 RSA 与 ElGamal 子模块实现具体算法。这样做的直接原因是证书验证和邮件协议都需要按证书中的算法标记选择签名引擎；如果上层分别调用两套不兼容的接口，证书链中混用 RSA 与 ElGamal 时会产生重复的分支代码。

`umbra_certificate` 包含证书对象、可信机构 TA、层次 CA 和证书库。`Certificate` 负责字段保存、txt 序列化、公钥文本转换和签名验证；`TrustedAuthority` 用于任务书的简单证书示例；`CertificateAuthority` 负责根证书自签名和下级证书签发；`CertificateLibrary` 在证书入库时检查签发者和信任根，并在查询时回溯出完整路径。`src/pki/pki_user` 中的 `PkiUser` 同时持有加密密钥对和签名密钥对，每个用户向所属 CA 申请两张用途不同的证书。

`umbra_mail` 只处理协议步骤，不负责网络、文件服务器或用户界面。它把签名邮件编码为带长度前缀的 `m || s`，提供发送端和接收端的组合接口。TUI 位于 `src/demo/umbra_demo.cpp`，通过后台线程调用同一组库接口，因此交互演示和测试使用的是相同的密码实现。

## 3. RSA 加密与签名

### 3.1 密钥生成

RSA 引擎在 `src/crypto/rsa_engine.cpp` 中实现。密钥生成使用 NTL 的 `GenPrime_ZZ` 生成两个不同的 1024 比特素数 `p` 和 `q`，并取 `e = 65537`。实现计算 `λ = lcm(p-1, q-1)`，在 `gcd(e, λ) = 1` 时求逆得到私钥指数 `d`。最终公钥为 `(n, e)`，其中 `n = p q`；私钥按任务书要求保存 `(p, q, d)`。解密时重新计算 `n`，因此私钥文本不需要重复存储模数。

任务书要求素性检测具有足够的重复次数。`GenPrime_ZZ` 内部使用 NTL 的概率素性检测；项目没有自行替换该检测流程，也没有把一个未经检测的随机数当作素数使用。测试和批处理演示会实际生成密钥，而不是读取预置的固定密钥。

交互式演示为了缩短启动等待时间，使用 256 比特的教学参数初始化 CA 和用户。批处理演示的 RSA 任务仍使用任务书规定的 1024 比特参数。这个差异只影响演示耗时和安全强度，不改变算法和接口。

### 3.2 分组加密和解密

加密时根据 `NumBytes(n) - 1` 计算分组长度，使每个明文块转换成的整数严格小于 `n`。每个块计算

```text
c = m^e mod n
```

密文采用文本格式，每行记录一个分组的原始字节数和密文整数：

```text
块长度-密文整数
```

解密端逐行读取，使用 `m = c^d mod n` 恢复整数，再按照记录的块长度调用 NTL 的字节转换函数还原原文。块长度字段保证最后一个分组的前导零不会丢失。

解密和验签接收的文本可能来自外部文件，也可能被人为篡改。实现先把 RSA 密文或签名整数约化到 `[0,n)`，再调用 `PowerMod`。这样错误输入会得到解密失败或验签失败，而不会因为 NTL 收到超出模数范围的底数而直接终止进程。

### 3.3 签名和验证

签名过程先计算 `H(m) = SHA-256(m)`，再计算

```text
s = H(m)^d mod n
```

验证端计算 `s^e mod n`，并与本地重新计算的摘要比较。摘要长度固定为 256 比特，因此签名运算的输入长度与邮件正文长度无关。RSA 签名和加密共用密钥对象格式，但在上层通过 `SignatureEngine` 与 `EncryptionEngine` 区分用途。

## 4. ElGamal 加密与签名

### 4.1 参数和密钥

ElGamal 引擎先生成素数 `q`，再令 `p = 2q + 1` 并检测 `p` 是否为素数，得到安全素数。随后随机选取 `r`，令 `α = r^2 mod p`，把运算限制在阶为 `q` 的二次剩余子群中。私钥 `a` 从 `[1,q-1]` 中选取，公钥计算为 `β = α^a mod p`，即公钥 `(p, α, β)`、私钥 `(p, α, a)`。

库的默认 ElGamal 参数为 2048 比特。由于安全素数生成在课程演示中耗时较长，批处理程序采用 512 比特，单元测试和交互式初始化采用 256 比特。报告中的测试结论针对实现逻辑，不把教学参数等同于生产安全参数。

### 4.2 分组加密和解密

ElGamal 使用与 RSA 相同的分组长度原则。每个明文块随机选择一次性密钥 `k`，计算

```text
c1 = α^k mod p
c2 = m · β^k mod p
```

文本密文每行记录 `块长度-c1-c2`。解密端先计算 `c1^a mod p`，再乘以其模逆得到 `m`。每个分组重新选择 `k`，所以同一明文的两次加密通常产生不同的密文，这也是概率加密行为的可观察结果。

### 4.3 ElGamal 签名和验证

签名前计算 SHA-256 摘要并约化到模 `q`。随机选取与 `q` 互素的 `k`，计算 `r = α^k mod p`，再计算

```text
s = k^(-1) · (H(m) - a r) mod q
```

验证使用教材中的关系式：

```text
α^H(m) ≡ β^r · r^s (mod p)
```

签名文本保存 `r` 和 `s` 两个整数。和 RSA 一样，验证端会先约化来自文本的 `r`，从而把错误公钥或篡改签名转化为稳定的验证失败。

## 5. 简单证书方案

### 5.1 字段映射

代码中的 `Certificate` 保存签发者 ID、主体 ID、主体公钥文本、签名、签名算法和公钥用途六项信息，分别对应任务书中的 `ID(TA)`、`ID(Alice)`、`ver_Alice`、`s`、`flag1` 和 `flag2`。`CryptoType::RSA` 与 `CryptoType::Elgamal` 的枚举顺序对应 `flag1` 的 0 和 1；`KeyPurpose::Encryption` 与 `KeyPurpose::Signature` 对应 `flag2` 的 0 和 1。

证书被序列化为 txt 文本，外层格式如下：

```text
BEGIN UMBRA CERTIFICATE
ISSUER:<issuer>
SUBJECT:<subject>
ALGORITHM:<RSA|Elgamal>
PURPOSE:<Encryption|Signature>
PUBLIC_KEY:<公钥类型标记及公钥文本>
SIGNATURE:
<签名文本>
END UMBRA CERTIFICATE
```

其中公钥文本第一行是 `RSA` 或 `ELGAMAL` 类型标记，后续行保存具体大整数。这个标记使证书链在 RSA 和 ElGamal 混用时能够直接选择解析器，不需要根据数字格式猜测算法。

### 5.2 签发和验证流程

`TrustedAuthority` 在构造时生成自己的签名密钥。签发证书时，TA 对主体 ID 和主体公钥文本组成的 `signed_payload()` 签名，再将签发者、用途和算法标记写入证书。验证端使用证书中的 `flag1` 选择对应签名引擎，并用 TA 公钥验证同一份被签名载荷。签发和验证共用载荷构造函数，避免两端因为换行或字段顺序不同而产生不一致。

测试覆盖 RSA TA 和 ElGamal TA 两种签发情形，同时检查 txt 序列化往返、证书篡改拒绝和错误签发者密钥拒绝。

## 6. 严格层次 PKI

### 6.1 建立层次

`CertificateAuthority` 为每个 CA 生成独立的签名密钥。根 `CA_root` 调用 `self_sign()` 生成自签名证书；根再分别为 `CA1` 和 `CA2` 签发证书；用户向所属 CA 申请两张证书，一张标记为加密用途，一张标记为签名用途。当前演示中，`CA1` 使用 ElGamal 签名，`CA2` 使用 RSA 签名，因此一条完整运行路径会同时经过两种算法。

证书库构造时保存受信根 ID 和根公钥。`store()` 只接受三类合法情况：受信根的自签名证书、已经存在于库中的 CA 签发的证书、以及能用已存储签发者公钥验证通过的用户证书。非受信根的自签名证书、找不到签发者的证书和签名不匹配的证书都会被拒绝，证书库不会把它们作为后续查询的信任来源。

### 6.2 查询与路径验证

`query(subject_id)` 返回从根到叶子的 `CertificatePath`。例如 Alice 的签名证书路径按顺序为 `CA_root -> CA1 -> Alice`。按用途查询的重载接口用于安全邮件：发送端查询接收者的加密证书，接收端查询发送者的签名证书。

路径验证先使用外部传入的受信根公钥验证根证书，再逐级从上一级证书解析公钥并验证下一级证书。任何一级失败都会使整条路径不可信。这个顺序把“证书存在”与“证书可信”分开处理，也使邮件模块不必自行实现 CA 层次判断。

### 6.3 用户对象

`PkiUser` 为每个用户分别生成加密密钥对和签名密钥对，并保存 CA 签发的两张证书。当前演示用户及算法如下：

| 用户 | 加密算法 | 签名算法 | 所属 CA |
| --- | --- | --- | --- |
| Alice | RSA | RSA | CA1 |
| Bob | ElGamal | RSA | CA2 |
| Eve | RSA | ElGamal | CA1 |

这种安排让邮件演示既覆盖 RSA 接收端，也覆盖 ElGamal 接收端，同时保留 Eve 作为切换用户和错误场景的可见对象。

## 7. 简易安全邮件系统

### 7.1 `m || s` 编码

邮件正文允许包含换行，不能简单地按某个换行符切开正文和签名。`sign_mail()` 采用长度前缀编码：

```text
<m 的字节长度>\n<m><s>
```

`parse_signed_mail()` 先读长度，再按字节数取出 `m`，余下部分作为签名 `s`。因此正文中包含换行、中文或空行时仍能确定边界。签名引擎接收正文 `m`，内部计算并签署 `SHA-256(m)`。

### 7.2 发送端

发送端 `send_mail()` 的实际顺序如下：

1. 在证书库中按接收者 ID 查询加密证书路径。
2. 用受信根公钥验证该路径。
3. 从叶证书解析接收者加密公钥。
4. 用发送者签名私钥对邮件摘要签名，得到 `s`。
5. 组装带长度前缀的 `m || s`，用接收者加密公钥得到密文 `c`。

接收者证书链验证失败时，流程在加密前抛出异常，不会把无法确认身份的邮件放入投递队列。

### 7.3 接收端

接收端 `receive_mail()` 先用自己的加密私钥解密 `c`，再解析出 `m` 和 `s`。随后按发送者 ID 查询签名证书路径，用受信根公钥验证路径，从叶证书取出签名公钥，最后验证 `s` 是否对应 `SHA-256(m)`。解密、证书链验证和签名验证全部通过后才返回正文；任一步失败都以异常报告，调用层可以拒绝显示邮件。

### 7.4 交互式 TUI

无参数运行 `umbra_demo` 会进入 ASCII TUI，启动时默认选中 Alice。左栏显示当前用户、收件箱和操作项，右栏显示后台加密过程日志。可以使用 `[3]` 或输入 `send` 撰写邮件，正文以单独一行的 `.` 结束；发送完成后切换到 Bob，使用 `[2]` 选择邮件并阅读。发送和阅读在后台线程运行，界面会显示 `QUERY CERT`、`SIGNING`、`ENCRYPTING`、`DECRYPTING` 等状态。

日志刻意只保留过程审计信息，例如“查询 Bob 的加密证书”“验证 3 张证书链”“生成签名 s，长度为若干字节”“将密文加入本地投递队列”。密钥数值、证书正文、邮件正文、签名和密文实际内容不会打印。这样既能说明协议执行顺序，也避免在演示画面中堆积无法核对的大整数。

## 8. 构建、运行与输入输出

### 8.1 依赖和预设

项目需要 CMake 3.23 或更高版本、Ninja、C++17 编译器、GMP 6.3.0 和 NTL 11.6.0。仓库只保留四个公开 CMake 预设：

| 预设 | 平台 | 配置 |
| --- | --- | --- |
| `debug` | Linux GCC | Debug |
| `release` | Linux GCC | Release |
| `windows-mingw-debug` | Windows MSYS2 UCRT64 MinGW | Debug |
| `windows-mingw-release` | Windows MSYS2 UCRT64 MinGW | Release |

Windows 不再提供 MSVC、x86 或单独的 x64 预设。Windows 脚本 `scripts/build_windows.ps1` 会准备 MSYS2 UCRT64 工具链和 GMP/NTL，并把构建目录映射到相应的 `build/windows-mingw-*`。MinGW 编译器运行时默认静态链接；因此在开启默认选项时，`umbra_demo.exe` 不需要把编译器 DLL 复制到旁边。GMP 和 NTL 也以静态库方式参与链接。

Linux 构建：

```bash
./scripts/build_deps.sh
cmake --preset debug
cmake --build --preset debug
ctest --preset debug
```

Windows 构建：

```powershell
.\scripts\build_windows.ps1
cmake --build --preset windows-mingw-debug
ctest --preset windows-mingw-debug
```

第一次使用 CMake 预设时要先执行 `cmake --preset windows-mingw-debug`；`cmake --build` 只编译已经配置好的目录。若 MSYS2 不在 `C:\msys64`，可以把安装目录传给脚本的 `-MsysRoot` 参数。

## 10. 设计决策、问题与改进

### 10.1 文本格式和长度前缀

课程设计要求密钥和密文具有文本转换能力，证书明确要求 txt 格式。项目没有把大整数直接写成二进制结构，而是为每种密钥定义稳定的逐行文本格式，并在证书公钥前加入算法标记。这样做便于检查、归档和在 RSA/ElGamal 混合证书链中选择解析器。

邮件正文可能包含任意换行，长度前缀比依赖分隔符更可靠。这个设计并不改变密码算法，只解决协议编码边界问题，使接收端能够确定摘要和验签所对应的原始字节串。

### 10.2 可信边界放在证书入库处

证书库在 `store()` 时就检查签发者、签名和受信根。查询接口因此只会从已通过入库校验的对象中构造路径，邮件模块可以专注于“查询路径、验证路径、取叶证书公钥”三个步骤。代价是证书入库顺序必须满足先根、再下级 CA、再用户证书；当前测试夹具和演示初始化都按这个顺序执行。

### 10.3 演示参数与安全参数

任务书的 RSA 参数要求为 1024 比特素数，批处理演示保持该要求。ElGamal 2048 比特安全素数生成对课堂演示过慢，因此交互初始化使用 256 比特、批处理使用 512 比特。它们只用于展示流程和验证代码，不能作为实际通信安全参数。若要面向真实应用，应提高参数规模，并采用经过标准化的填充和密钥管理方案。

### 10.4 Windows 构建问题的处理

原项目的预设混合了 Linux、MSVC、x86、x64 和 MinGW，容易使第一次构建的人选到不匹配的编译器和依赖。当前配置只保留 Linux GCC 和 Windows MSYS2 UCRT64 MinGW，并让 Windows 脚本统一准备同一 ABI 的 GMP/NTL。默认静态链接 MinGW 编译器运行时，减少“程序启动后找不到 DLL”的部署问题。该处理不会把 GMP/NTL 的算法逻辑嵌入源代码，也不等同于把所有第三方组件永久合并成一个不可替换的二进制；它只是明确了构建和运行时的部署边界。

### 10.5 尚未实现的生产特性

当前实现服务于课程算法和协议演示，不是生产级密码库。证书没有有效期、吊销列表和扩展字段，证书库没有持久化和并发访问控制，邮件队列也只存在于进程内。RSA 未实现 OAEP/PSS，密钥文件没有加密保护，ElGamal 参数和签名格式也未按照生产协议封装。后续若继续扩展，应先补充标准化编码、密钥保护、证书生命周期和持久化存储，再考虑网络传输和更复杂的用户界面。

## 11. 总结

当前项目已经把任务书要求的 RSA、ElGamal、简单证书、严格层次 PKI 和安全邮件组织为一条可运行的实现链。算法、证书、CA、用户和邮件分别由独立类与源文件实现，CMake 将它们编译为分层库，9 个测试目标负责验证正常流程和主要反例。Windows 侧只保留 MinGW 预设并默认静态链接编译器运行时，Linux 侧保留 GCC Debug/Release 预设；交互演示通过 ASCII TUI 让发送和接收过程可操作，同时用后台日志展示证书查询、摘要、签名、加密、解密和验签的先后关系。
